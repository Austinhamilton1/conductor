# Command Queue Architecture

The Command Queue provides deferred structural modification of the simulation state.

Systems can modify the values of components they currently access, but operations that change the structure of the ECS are queued and applied after system execution.

This separation gives Conductor a stable simulation state during system execution and provides a foundation for future parallel and GPU execution.

## Why Commands Exist

Some simulation operations modify existing data:

```cpp
position.x += velocity.x * dt;
```

Other operations change the structure of the simulation:

```cpp
add_component(entity, Battery{});
remove_component<Velocity>(entity);
create_entity();
destroy_entity(entity);
```

Structural operations can invalidate the data structures that systems are currently iterating.

For example:

```text
System
  │
Iterating Position storage
  │
  +-- entity A
  +-- entity B
  │
  +-- add/remove component
           │
      Storage changes
           │
    Iterator may no longer
    represent the same state
```

Conductor avoids this problem by deferring structural operations.

```text
System execution
      │
Queue command
      │
System execution completes
      │
Apply commands
      │
New simulation structure
```

The Command Queue therefore acts as a synchronization boundary between system execution and structural mutation.

## Structural vs. Non-Structural Changes

The distinction between ordinary data changes and structural changes is fundamental.

### Non-structural changes

Changing the contents of an existing component does not change the ECS structure.

For example:

```cpp
position.x += velocity.x * dt;
position.y += velocity.y * dt;
```

This can occur directly through a system's query.

### Structural changes

Structural changes alter the relationship between entities and components.

Examples include:

* creating an entity
* destroying an entity
* adding a component
* removing a component

These operations are deferred.

```text
             Simulation State
                    │
          +-------------------+
          │                   │
    Data modification    Structural change
          │                   │
      Immediate           CommandQueue
                              │
                         Later application
```

## Command Queue Ownership

The Command Queue is owned by the World.

Systems receive access to it through their `SystemContext`.

This keeps structural mutation under World control without giving systems direct access to ECS internals.

```text
World
 │
 +-- Component Storage
 │
 +-- Entity Manager
 │
 +-- CommandQueue
        │
        │ SystemContext
        │
     Systems
```

A system therefore requests structural changes rather than directly manipulating storage.

## Commands

A command represents one deferred operation.

Conceptually:

```text
Command
+-- Operation
+-- Target entity / reference
+-- Operation data
```

Commands are designed to be simple, copyable data.

This is intentional.

The Command Queue is intended to be independent of the execution mechanism that produces it. Commands can therefore be generated by systems without requiring those systems to perform the structural operation immediately.

The data-oriented command representation also provides a path toward future execution backends.

## Creating Commands

Systems can enqueue structural operations through their command interface.

For example:

```cpp
ctx.commands().add_component(
    entity,
    Battery{100.0f}
);
```

The system does not receive the newly added component immediately as a consequence of that command.

Instead, the request remains deferred until command processing occurs.

This means systems should reason about the current simulation state while executing, not assume that structural commands have already taken effect.

## Command Processing

Commands are processed after scheduler execution reaches the appropriate synchronization point.

Conceptually:

```text
World::update()
      │
Scheduler
      │
      +-- System A
      +-- System B
      +-- System C
      │
Command Queue
      │
      +-- Entity commands
      +-- Component commands
      │
Apply structural changes
      │
Next simulation state
```

This gives the simulation a clear frame boundary:

```text
        Current State
             │
       System execution
             │
       commands queued
             │
      Command processing
             │
         New State
```

## Entity Commands

Entity commands operate on entity lifetime.

Examples include:

* creating an entity
* destroying an entity

Entity operations are processed before component operations.

Conceptually:

```text
Entity commands
      │
Component commands
```

This ensures that component operations can reference entities whose creation or destruction has already been resolved during command processing.

The ordering among entity commands themselves is not intended to provide arbitrary application-level ordering beyond the guarantees defined by the command processing rules.

## Component Commands

Component commands modify the component structure of existing entities.

Examples include:

```text
Add Position
Remove Velocity
Add Battery
Remove Sensor
```

Component commands are processed after entity commands.

This gives command processing a simple structural sequence:

```text
1. Resolve entity operations
            │
2. Resolve component operations
            │
3. Updated ECS structure
```

The order among commands within those categories should not be treated as a general-purpose ordering mechanism.

If a simulation requires a specific ordering relationship, that relationship should be represented explicitly in the simulation architecture.

## Deferred Entities

A command queue must sometimes refer to an entity that does not yet have a normal runtime identity.

For example, a system may create an entity and then want to add components to that new entity during the same command batch.

Conductor supports this using a deferred entity reference.

Conceptually:

```text
Create Entity
      │
Deferred Entity Reference
      │
      +-- Add Position
      +-- Add Velocity
      +-- Add Battery
      │
Command processing
      │
Actual Entity created
      │
Component commands resolved
```

The deferred reference acts as a lightweight identifier that can be used by subsequent commands before the actual entity exists.

This avoids forcing systems to perform immediate entity creation merely to obtain an entity ID.

## Deferred Entity Lifetime

A deferred entity reference represents a pending entity operation rather than an already-live entity.

Systems should therefore not treat it as equivalent to an ordinary `Entity` during the same execution phase.

Its purpose is to connect commands within the deferred command sequence.

```text
Normal Entity
    │
    +-- already exists

Deferred Entity
    │
    +-- will exist after command processing
```

Once command processing completes, the resulting entity becomes part of the normal ECS state.

## Command Ordering

The Command Queue guarantees the broad structural ordering required by the ECS:

```text
Entity commands
      │
Component commands
```

However, the Command Queue should not be treated as a general-purpose transactional scripting system.

In particular, code should not rely on arbitrary ordering between commands within the same category unless that ordering is explicitly guaranteed by the implementation.

For example, simulation logic should not depend on unrelated component commands being processed in a particular order.

If execution ordering matters, it should be represented by the appropriate engine mechanism, such as system dependencies.

## Invalid Commands

Commands are validated when they are applied.

A command may be invalid because, for example:

* its target entity is no longer valid
* a required component does not exist
* a component is being added where the operation is invalid
* a deferred reference cannot be resolved

Invalid command processing is treated as a simulation error rather than silently ignoring the invalid operation.

The command processing model is designed so that an invalid command causes the command application operation to fail rather than leaving the simulation in an ambiguous partially-applied state.

This provides a strong invariant:

> **Command processing either produces the intended structural transition or reports failure.**

The exact error-handling policy may evolve as the runtime develops, but invalid structural operations should never be silently accepted.

## Commands and System Execution

The command queue allows systems to separate immediate computation from deferred structural work.

For example, a system might determine that an entity should receive a new component:

```cpp
for (auto [position] : ctx.query()) {
    if (should_spawn_sensor(position)) {
        ctx.commands().add_component(
            entity,
            Sensor{}
        );
    }
}
```

The system can continue processing its current query without modifying the underlying component structure while that query is active.

After the appropriate synchronization point, the queued command is applied.

This keeps the execution phase stable.

## Commands and Scheduling

Commands are closely related to the Scheduler.

The Scheduler controls system execution:

```text
Scheduler
    │
System execution
```

The Command Queue handles structural changes generated by that execution:

```text
System
    │
CommandQueue
    │
Structural update
```

Together they form the execution loop:

```text
              +-------------------+
              │   Current State   │
              +-------------------+
                        │
              +-------------------+
              │    Scheduler      │
              +-------------------+
                        │
              +-------------------+
              │     Systems       │
              +-------------------+
                        │
                queue commands
                        │
              +-------------------+
              │   Command Queue   │
              +-------------------+
                        │
                  apply changes
                        │
              +-------------------+
              │    New State      │
              +-------------------+
```

The Scheduler and Command Queue therefore provide two complementary forms of control:

* **Scheduler:** controls when behavior executes.
* **Command Queue:** controls when structural changes become visible.

## Multithreading

The deferred command model also provides a foundation for future multithreaded system execution.

If multiple systems execute concurrently, allowing every system to immediately modify ECS structure would create significant synchronization requirements.

Instead, systems can produce commands independently:

```text
System A -----+
              │
System B -----+---> Command Queue
              │
System C -----+
                    │
             Synchronization
                    │
             Structural update
```

The current implementation does not require the scheduler to execute systems concurrently.

The command architecture is nevertheless designed so that deferred structural work does not inherently depend on single-threaded system execution.

## GPU and Future Backends

Commands are also deliberately represented as simple data rather than tightly coupling structural operations to arbitrary C++ object behavior.

This is useful for future execution backends.

A future backend could potentially produce command buffers that are processed independently from the system that generated them:

```text
CPU / GPU System
       │
Command Data
       │
Command Processing
       │
ECS State
```

The current CPU implementation is the primary execution path. GPU execution is a future architectural direction rather than a requirement of the current kernel.

The command model is designed to avoid making that future direction impossible.

## Command Queue Lifecycle

The Command Queue follows the lifetime of the World.

```text
World created
      │
CommandQueue created
      │
Systems enqueue commands
      │
Commands processed
      │
Next simulation step
      │
World destroyed
      │
CommandQueue destroyed
```

Commands are therefore part of simulation state transition rather than an independent application-level subsystem.

## Design Goals

The Command Queue is designed around several principles.

### Stable system iteration

Systems should be able to iterate over component storage without simultaneously changing its structure.

### Deferred structural mutation

Structural operations become visible at a defined synchronization point rather than at arbitrary moments during system execution.

### Simple command representation

Commands remain simple data so they can be efficiently queued and potentially processed by different execution backends.

### Clear ordering guarantees

Entity operations are resolved before component operations, while callers should not depend on unspecified ordering within those categories.

### Failure visibility

Invalid structural operations are treated as errors rather than silently ignored.

### Future parallelism

Systems can generate structural work independently of when that work is ultimately applied.

## Command Queue Mental Model

The Command Queue can be summarized as:

```text
             SYSTEM
                │
                │ requests
                |
       +-----------------+
       │  Command Queue  │
       +-----------------+
                │
         synchronization
                │
       +-----------------+
       │  Entity Changes │
       +-----------------+
                │
       +------------------+
       │ Component Changes│
       +------------------+
                │
          Updated ECS
```

The command queue is the mechanism that separates **simulation computation** from **simulation structure mutation**.

## Design Principle

The central idea behind the Conductor Command Queue is:

> **Systems can request structural changes during execution, but those changes do not become part of the ECS until the appropriate synchronization point.**

This gives Conductor a stable execution model today while providing architectural room for multithreaded and GPU-backed execution in the future.
